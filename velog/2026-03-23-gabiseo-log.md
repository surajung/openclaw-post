# Docker 스택 설계 원본과 n8n 워크플로우를 분리해 운영하는 방법

#OpenClaw #Docker #n8n #인프라 #자동화

## 한줄 요약
OpenClaw에서 사용하는 인프라를 Git 기반으로 관리하는 구조를 정리했다.

## 배경

개인 자동화 환경이 커질수록 Docker 스택, n8n 워크플로우, 운영 중인 실제 런타임 디렉토리가 한곳에 뒤섞이기 쉽습니다. 처음에는 빠르게 붙여 쓰는 편이 편하지만, 시간이 지나면 "현재 운영 중인 설정"과 "다음에 반영할 설계 원본"이 섞이면서 수정 기준점이 불명확해집니다.

이번에는 이 문제를 줄이기 위해 인프라 관리용 워크스페이스 구조를 다시 정리했습니다. 핵심은 두 가지였습니다.

1. Docker 스택 설계 원본을 별도 `infra/` 디렉토리에서 관리한다.
2. n8n 워크플로우도 GUI 의존도를 낮추고 JSON export를 파일로 관리한다.

## 문제

기존 방식에는 몇 가지 불편이 있었습니다.

- 실제 운영 디렉토리와 설계 원본의 경계가 모호했다.
- n8n 설정이 GUI 안에만 있으면 변경 이력 추적이 어렵다.
- 초안, 실험본, 게시용 문서가 같은 성격으로 보관되면서 저장 위치 규칙이 약했다.
- 운영 환경에서 급하게 수정한 내용이 문서와 어긋나기 쉬웠다.

특히 Docker 기반 서비스는 한 번 돌아가기 시작하면 당장 불편하지 않아 보이지만, 나중에 복구하거나 다른 장비로 옮길 때 "무엇이 진짜 기준본인지"가 가장 큰 문제가 됩니다.

## 변경 내용

이번 정리에서 적용한 구조는 아래와 같습니다.

### 1) 인프라 설계 원본 디렉토리 표준화

`infra/` 아래에 템플릿과 서비스별 스택 초안을 분리했습니다.

```text
infra/
  templates/
  stacks/
    rsshub/
    n8n/
```

이 구조에서 `templates/`는 재사용 가능한 기본 compose/env 템플릿을 두는 공간이고, `stacks/`는 서비스별 설계 원본을 보관하는 공간입니다.

운영 중인 실제 디렉토리는 별도로 두고, `infra/`는 Git으로 관리되는 설계 원본 저장소 역할만 하도록 방향을 잡았습니다.

### 2) n8n 스택을 운영 설정과 동기화

n8n 스택은 실제 운영 중이던 구성에서 필요한 내용을 추려 `infra/stacks/n8n/docker-compose.yml`에 반영했습니다. 여기에는 다음 요소를 포함했습니다.

- n8n 본체
- Cloudflare Tunnel 컨테이너
- 영속 볼륨 마운트
- `.env` 기반 환경변수 분리
- 타임존 및 웹훅 URL 설정

핵심은 "운영에서 이미 검증된 설정을 설계 원본으로 되돌려놓는 것"이었습니다. 이렇게 해야 다음 수정부터는 운영 디렉토리가 아니라 설계 저장소를 먼저 수정하는 흐름으로 바꿀 수 있습니다.

### 3) n8n 워크플로우 파일 관리 규칙 정리

n8n 워크플로우는 `infra/n8n/workflows/`를 기준본 저장 위치로 정했습니다.

- `workflows/`: 운영 기준 JSON export
- `notes/`: 입출력 스키마, 설계 메모, 운영 메모
- `archive/`: 참고용 보관본

이렇게 분리하면 "실제로 복원 가능한 기준본"과 "설명 문서"를 나눠서 관리할 수 있습니다. AI로 workflow를 읽고 수정하는 작업도 훨씬 수월해집니다.

### 4) 문서와 운영 기준본의 역할 분리

게시 가능한 문서 초안과 n8n 운영 기준본이 섞이지 않도록 디렉토리 정책도 함께 정리했습니다.

- `posts/`: 공개 검토 대상 문서 초안
- `infra/n8n/notes/`: 설계 문서, 입출력 스키마, 운영 메모
- `infra/n8n/workflows/`: 확정된 workflow JSON 기준본

이 규칙은 사소해 보이지만 실제로는 꽤 중요합니다. 파일 경로만 봐도 "이게 게시용 문서인지, 설명 문서인지, 실제 운영 기준본인지"를 구분할 수 있기 때문입니다.

## 핵심 설정 / 코드

이번에 기준본으로 정리한 n8n 스택의 핵심 compose는 아래와 같은 형태입니다.

```yaml
version: '3.8'

services:
  n8n:
    image: n8n.io/n8n
    restart: always
    ports:
      - "5678:5678"
    environment:
      - N8N_HOST=${N8N_HOST}
      - N8N_PORT=5678
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=${WEBHOOK_URL}
      - GENERIC_TIMEZONE=Asia/Seoul
      - N8N_ENCRYPTION_KEY=${N8N_ENCRYPTION_KEY}
    volumes:
      - ./data:/home/node/.n8n
    networks:
      - n8n_network
    env_file:
      - ./.env

  cloudflared:
    image: cloudflare/cloudflared:latest
    restart: always
    command: tunnel run
    environment:
      - TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}
    networks:
      - n8n_network
    env_file:
      - ./.env

networks:
  n8n_network:
    driver: bridge
```

이 설정에서 눈여겨볼 부분은 다음과 같습니다.

- 비밀값은 compose에 직접 넣지 않고 `.env`로 분리
- 외부 공개 웹훅 경로는 `WEBHOOK_URL`로 명시
- `cloudflared`를 별도 서비스로 두어 외부 진입 경로를 분리
- 워크플로우 본문이 아니라 스택 자체도 Git 관리 대상으로 승격

문서 측면에서는 인프라 워크스페이스의 원칙도 함께 정리했습니다.

```text
- 설계 원본/템플릿 저장소로 사용
- 실제 운영 스택은 workspace 밖에 둘 수 있음
- 민감 정보는 커밋 금지
- 이 환경에서는 docker compose 대신 docker-compose 사용 우선
```

이런 규칙을 README 수준에서 먼저 고정해 두면, 이후 자동화나 협업 도구가 같은 전제를 공유하기 쉬워집니다.

## 결과

정리 이후 얻은 효과는 명확했습니다.

- Docker 스택의 기준본 위치가 분명해졌다.
- n8n 워크플로우를 파일 기반으로 추적할 수 있게 됐다.
- 운영 디렉토리와 설계 저장소의 역할이 분리됐다.
- 게시 초안과 실험 산출물의 경계가 명확해졌다.
- 이후 AI 보조 편집이나 Git 기반 변경 검토가 쉬워졌다.

특히 "운영에서 우연히 맞아떨어진 설정"을 그대로 방치하지 않고, 설계 원본으로 환원했다는 점이 중요했습니다. 이 과정이 있어야 다음 변경부터는 복제 가능한 방식으로 인프라를 다룰 수 있습니다.

## 정리

개인 자동화 환경도 규모가 커지면 결국 작은 플랫폼 운영과 비슷한 문제가 생깁니다. 어디가 기준본인지, 어떤 파일이 배포 대상인지, 어떤 산출물이 공개용인지가 불분명하면 운영 속도보다 복구 비용이 더 커집니다.

이번 작업은 새 기능을 추가한 날이라기보다, 앞으로의 변경을 덜 위험하게 만들기 위한 구조 정리에 가까웠습니다. 하지만 이런 정리가 쌓여야 n8n, RSSHub, Docker 스택, 문서화 흐름을 한 번에 다룰 수 있는 기반이 만들어집니다.
