# 오전 리포트 이상 현상을 추적할 때 n8n과 OpenClaw cron, macOS 절전을 분리해서 본 이유

#OpenClaw #n8n #cron #macOS #운영

## 한줄 요약
오전 리포트 이상 현상을 한 덩어리 장애로 보지 않고 `n8n 데이터 수집`, `OpenClaw cron 실행`, `macOS 깨우기 스케줄`로 분리해 진단하면서 실제 원인을 더 빠르게 좁혔다.

## 배경
5월 24일 아침, 오전 리포트가 23일부터 이상하게 온다는 제보를 기준으로 운영 경로를 다시 점검했다.

겉으로 보면 "아침 브리핑이 이상하다"는 하나의 증상이지만, 실제 파이프라인은 여러 층으로 나뉘어 있었다. 일부 데이터는 n8n webhook에서 가져오고, 메시지 생성은 OpenClaw cron이 맡고, 이 모든 흐름은 호스트가 새벽에 정상적으로 깨어 있어야 성립한다.

그래서 이번 점검은 서비스 전체를 한 번에 의심하기보다, 어디까지가 n8n 문제이고 어디부터가 OpenClaw 실행 경로 문제인지 먼저 분리하는 방식으로 진행했다.

## 문제
이번에 확인한 문제는 크게 세 갈래였다.

- `n8n 워크플로에서 LLM을 제거한 변경`이 오전 리포트 이상의 직접 원인인지 불명확했다.
- 실제 이상하게 보인 메시지 중 일부는 데이터 수집 실패보다 `운영 리포트 3차 메시지의 포맷 통제`가 약한 문제에 가까웠다.
- 아침 자동화가 제시간에 돌려면 호스트의 반복 wake/sleep 스케줄도 맞아 있어야 하는데, 현재 스케줄이 원하는 값과 달랐다.

즉, "아침 리포트가 이상하다"는 증상만으로는 원인을 특정할 수 없었고, 수집 계층과 생성 계층, 호스트 전원 계층을 각각 따로 봐야 했다.

## 변경 내용
- 아침 브리핑을 3개 job으로 나눠 보고, 각 job의 의존성을 다시 정리했다.
- `n8n LLM 제거`와 `OpenClaw cron의 LLM 호출`을 같은 문제로 묶지 않고 분리해서 판단했다.
- 2차 브리핑은 webhook 실패 시에도 빈 문구로 끝나지 않도록 `web_search 기반 대체수집` 규칙을 유지하는 구조로 봤다.
- 3차 운영 리포트는 출력 형식을 더 강하게 제한해, 확인 가능한 정보만 짧게 쓰도록 정리된 상태를 확인했다.
- macOS 전원 스케줄은 `pmset`으로 조회해 현재 wake/sleep 시간이 실제로 어떻게 잡혀 있는지 점검했다.

핵심은 "한 군데를 고치면 전체가 해결된다"는 식으로 접근하지 않았다는 점이다. 이번 작업에서는 데이터 소스, LLM 실행 경로, 호스트 상태를 따로 떼어 보는 편이 훨씬 유효했다.

## 핵심 설정 / 코드
현재 구조를 이해하는 데 중요한 부분만 추리면 아침 자동화는 대략 이런 형태였다.

```json
[
  {
    "name": "daily-briefing-telegram-6am",
    "schedule": "0 6 * * *",
    "responsibility": "날짜/날씨/일정/핵심 뉴스"
  },
  {
    "name": "daily-links-geeknews-telegram-6h02",
    "schedule": "2 6 * * *",
    "responsibility": "watchlist-summary, geeknews-summary",
    "fallback": "web_search"
  },
  {
    "name": "daily-ops-report-telegram-6h04",
    "schedule": "7 6 * * *",
    "responsibility": "운영 상태 요약"
  }
]
```

2차 브리핑은 webhook 실패를 그대로 사용자 메시지 품질 저하로 연결하지 않도록 설계돼 있었다.

````text
1) watchlist-summary / geeknews-summary webhook 최대 2회 시도
2) {"message":"Error in workflow"} / timeout / parse_error면 실패 판정
3) 실패 시 web_search로 대체수집
4) 대체수집도 실패할 때만 최종 실패 문구 사용
````

운영 리포트는 "많이 설명하는 것"보다 "형식을 고정하는 것"이 중요했다.

```text
운영 리포트: 정상, 특이사항 없음
Velog 초안: 생성 완료
```

호스트 상태 점검에는 macOS 기본 도구를 그대로 썼다.

````bash
pmset -g sched
pmset -g assertions | sed -n '1,80p'
```` 

실제 조회 결과에서는 반복 전원 스케줄이 아래처럼 잡혀 있었다.

```text
wake at 5:30AM every day
sleep at 1:00AM every day
```

반면 원하는 시각으로 변경하는 명령은 루트 권한이 없어서 바로 적용되지 않았다.

```text
pmset: Must be run as root to modify settings
```

## 결과
이번 점검으로 얻은 결론은 비교적 명확했다.

- `n8n에서 LLM을 제거한 것` 자체는 이번 이상 현상의 핵심 원인으로 보이지 않았다.
- 실제로 이상하게 보인 운영 리포트는 OpenClaw 쪽 3차 메시지의 포맷 문제 성격이 더 컸다.
- 1차, 2차 브리핑의 실패 가능성은 n8n보다 OpenClaw 모델 호출 경로의 타임아웃/쿼터 영향이 더 직접적이었다.
- 호스트 스케줄은 원하는 `05:00 wake / 00:00 sleep`이 아니라 `05:30 wake / 01:00 sleep`으로 남아 있었고, 루트 권한 없이 수정되지 않았다.

특히 `pmset -g assertions`에서 `PreventUserIdleSystemSleep = 1`과 `NoIdleSleepAssertion`이 보인 점은, 단순히 스케줄만 볼 것이 아니라 실제 절전 방지 상태도 함께 확인해야 한다는 신호였다.

## 정리
운영 자동화가 이상할 때 가장 흔한 실수는 모든 증상을 하나의 원인으로 묶는 것이다. 하지만 이번 사례에서는 `n8n 데이터 수집`, `OpenClaw cron 실행`, `macOS 전원 상태`가 서로 다른 고장 지점을 만든다는 점이 분명했다.

실무적으로는 아래 순서가 더 낫다.

- 데이터 소스 계층과 메시지 생성 계층을 먼저 분리한다.
- 사용자에게 보이는 이상 문구가 포맷 문제인지 실제 수집 실패인지 구분한다.
- 마지막으로 호스트 wake/sleep과 sleep assertion까지 확인해 스케줄러가 돌 물리적 조건이 맞는지 본다.

아침 자동화처럼 여러 시스템이 이어진 작업은 "어디가 실패했는지"보다 먼저 "어떤 층이 실패했는지"를 구분해야 복구 속도가 빨라진다.
