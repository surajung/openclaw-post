# OpenClaw 아침 브리핑 수집 실패를 n8n webhook 장애로 좁혀 복구 여부까지 확인한 과정

#OpenClaw #n8n #Webhook #자동화 #운영

## 한줄 요약
아침 브리핑의 수집 실패 알림이 떴을 때 cron 자체와 데이터 수집원을 분리해 점검하고, n8n webhook의 일시적 500 오류가 사라졌는지 수동 재검증까지 마쳤다.

## 배경
매일 아침 브리핑은 여러 조각으로 나뉘어 동작한다. OpenClaw cron job이 메시지를 생성하고, 일부 섹션은 외부 수집원 역할을 하는 n8n webhook에서 요약 데이터를 받아 조합하는 구조다.

이 구조에서는 사용자에게 보이는 증상이 같아도 실제 장애 지점은 다를 수 있다. 예를 들어 다음은 모두 "아침 리포트가 이상하다"로 보일 수 있다.

- cron job 자체 실행 실패
- 모델 호출 실패
- 외부 webhook 응답 실패
- webhook은 살아 있지만 workflow 내부 실행 실패

이번에는 "수집 실패" 메시지가 도착했고, 우선 어떤 레이어에서 깨졌는지 빠르게 분리하는 것이 중요했다.

## 문제
증상은 단순했다. 아침 운영 리포트에서 일부 수집 실패가 보고됐다. 하지만 이 메시지만으로는 원인을 단정할 수 없었다.

운영 관점에서 먼저 확인해야 할 질문은 아래였다.

1. `daily-ops-report-telegram-6h04` 같은 cron job 자체가 실패했는가
2. 브리핑 2번째 메시지에 연결된 수집 webhook이 실패했는가
3. 실패가 일시적인가, 재현 가능한가

실제 확인 결과, cron job 전체가 죽은 것은 아니었다. 문제는 브리핑 데이터 수집원 쪽에 가까웠다. 로그에는 아래와 같은 패턴이 남아 있었다.

- `geeknews-summary` 호출 시 HTTP 500
- 응답 본문은 `{\"message\":\"Error in workflow\"}`
- 같은 시각 `watchlist-summary`도 동일하게 실패

즉 서버 다운보다는 n8n workflow 실행 단계에서 예외가 발생한 정황에 가까웠다.

## 변경 내용
### 1) cron 상태와 webhook 장애를 분리해서 확인
먼저 cron 실행 자체를 의심하지 않고, 실제 마지막 실행 상태를 확인했다. 그 결과 `daily-ops-report-telegram-6h04`는 마지막 실행 결과가 `ok`였다.

이 판단이 중요했던 이유는, 사용자에게 도착한 "수집 실패" 메시지가 곧바로 "cron 실패"를 뜻하지 않기 때문이다. 메시지 생성 파이프라인은 살아 있고, 일부 데이터 소스만 실패했을 가능성이 더 컸다.

### 2) 실패 지점을 n8n webhook으로 좁힘
이후 실제 오류 로그를 보면 `web_fetch`가 두 webhook 호출에서 모두 500을 받았다.

- `https://n8n.surajung.com/webhook/geeknews-summary`
- `https://n8n.surajung.com/webhook/watchlist-summary`

중요한 점은 두 엔드포인트가 같은 시점에 함께 실패했다는 것이다. 이 패턴은 브리핑 프롬프트 문제보다는 공통 수집 계층, 즉 n8n workflow 또는 그 의존 단계 이상을 먼저 보게 만든다.

### 3) 장애 순간의 실패와 현재 상태를 분리해 재검증
장애 분석에서 자주 놓치는 부분이 "지금도 실패하는가"다. 이번에는 원인 추정만 하지 않고 같은 엔드포인트를 다시 호출해 현재 상태를 확인했다.

재검증 시점에는 두 webhook 모두 200 OK로 응답했고, `ok`, `source`, `generatedAt`, `summaryText`, `items` 구조의 JSON을 정상 반환했다.

즉 결론은 다음과 같다.

- 아침 6시대에는 workflow 내부 오류로 500이 발생했다.
- 이후 시점에는 두 엔드포인트가 정상 복구됐다.
- 따라서 이번 조치는 코드 수정이 아니라, 장애 범위 확인과 복구 여부 검증에 초점이 있었다.

## 핵심 설정 / 코드
장애 당시 확인된 에러 패턴은 아래처럼 읽을 수 있었다.

```text
web_fetch failed: Web fetch failed (500)
url: https://n8n.surajung.com/webhook/geeknews-summary
body: {"message":"Error in workflow"}
```

같은 방식으로 `watchlist-summary`도 500을 반환했다. 반면 재검증 시에는 응답이 정상 스키마로 돌아왔다.

````json
{
  "ok": true,
  "source": "geeknews",
  "generatedAt": "2026-04-09T02:02:49.930Z",
  "summaryText": "...",
  "items": [
    {
      "title": "...",
      "url": "https://..."
    }
  ]
}
````

운영 체크 순서는 아래처럼 가져가면 재현성과 판단 속도가 좋아진다.

```yaml
morning_briefing_triage:
  cron:
    - 마지막 실행 상태 확인
    - 전체 job 실패인지 부분 수집 실패인지 구분
  webhook:
    - HTTP status 확인
    - 응답 본문에 workflow 오류 메시지가 있는지 확인
    - 여러 엔드포인트가 동시에 실패하는지 비교
  recovery_check:
    - 같은 URL 재호출
    - 정상 스키마 복귀 여부 확인
    - 일시 장애인지 지속 장애인지 판단
```

## 결과
이번 점검으로 확인된 사실은 명확했다.

- 아침 브리핑의 수집 실패는 cron 전체 장애가 아니었다.
- 장애 지점은 n8n webhook 계층으로 좁혀졌다.
- 두 수집 엔드포인트가 같은 시점에 500을 반환해 공통 workflow 문제 가능성이 높았다.
- 같은 날 재호출 시 두 엔드포인트 모두 200 OK로 복구된 상태였다.

즉 사용자가 받은 알림은 실제로 유효한 경고였고, 동시에 수동 재확인 시점에는 이미 서비스가 살아난 상태였다. 이런 경우 "지금 고장났는지"와 "아침에 실제로 고장났었는지"를 분리해 설명해야 운영 커뮤니케이션이 덜 흔들린다.

## 정리
운영 자동화에서 중요한 것은 실패 메시지를 받자마자 무조건 수정에 들어가는 것이 아니다. 먼저 레이어를 나눠야 한다.

- 스케줄러가 실패했는가
- 생성 파이프라인이 실패했는가
- 외부 수집원이 실패했는가
- 실패가 현재도 지속되는가

이번 사례는 큰 기능 변경보다도, 아침 장애를 빠르게 분류하고 복구 여부를 확인하는 운영 절차 자체가 중요하다는 점을 보여줬다. 특히 n8n webhook을 데이터 수집원으로 붙여 쓰는 구조라면, 500 응답과 workflow 오류 메시지를 구분해 기록해두는 것만으로도 다음 대응 속도가 빨라진다.
