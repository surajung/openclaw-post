# n8n webhook이 "복구된 것처럼" 보여도 다음날 다시 실패한 이유를 운영 관점에서 다시 본 기록

#OpenClaw #n8n #Webhook #운영 #장애분석

## 한줄 요약
아침 브리핑 수집 장애가 하루 만에 재발하자, 전날의 일시 복구 확인만으로는 충분하지 않다는 점을 기준으로 장애를 다시 추적했고, 같은 webhook이 아침에는 실패하고 뒤늦게는 정상 응답하는 간헐 패턴을 확인했다.

## 배경
아침 브리핑 자동화는 OpenClaw cron이 메시지를 생성하고, 일부 섹션은 n8n webhook에서 요약 데이터를 받아 조합하는 구조로 돌아간다.

전날에도 브리핑 수집 실패가 있었고, 당시에는 `watchlist-summary`, `geeknews-summary` webhook이 500 오류를 낸 뒤 수동 재확인 시점에는 200 OK로 복구된 상태였다. 문제는 여기서 끝나지 않았다. 다음날 아침에도 같은 종류의 수집 실패 메시지가 다시 들어왔다.

운영 관점에서 이 상황은 단순 재장애가 아니라, "복구처럼 보이는 순간"과 "실제 안정화"를 구분해야 하는 케이스에 가깝다.

## 문제
사용자 입장에서는 질문이 명확했다. 전날 이상 없다고 했는데 왜 오늘도 같은 실패가 발생했는가.

이 질문에 답하려면 단순히 "지금은 응답된다"를 다시 말하는 것이 아니라 아래를 확인해야 했다.

- 전날 장애가 정말 해결된 것인지
- 아니면 workflow가 간헐적으로 실패하고 있었는지
- 아침 cron 실행 시점과 나중 수동 점검 시점의 상태가 달랐는지

실제 전날 06시대 실행 기록을 보면 `watchlist-summary`, `geeknews-summary`가 모두 `500`과 `{"message":"Error in workflow"}`를 반환했다. 그런데 같은 날 08시 20분대 재실행에서는 두 webhook이 모두 정상 JSON을 돌려줬다.

즉 전날의 결론은 "완전 해결"이 아니라 "그 시점에는 응답이 정상으로 돌아와 있었다"가 더 정확했다. 이번 재점검의 핵심은 바로 그 표현 차이를 기술적으로 분리하는 것이었다.

## 변경 내용
### 1) 장애 판단 기준을 `현재 응답 여부`에서 `시간대별 패턴`으로 바꿨다
단발성 수동 점검은 특정 시점의 상태만 보여준다. 이번에는 아침 cron 실행 시점과 후속 수동 재검증 시점을 분리해서 봤다.

그 결과 패턴은 아래처럼 정리됐다.

- 06:02 전후: 두 webhook 모두 500 / `Error in workflow`
- 08:20 전후: 두 webhook 모두 200 OK, 정상 JSON 반환

이 패턴은 외부 엔드포인트가 완전히 죽어 있는 장애라기보다, workflow 내부 실행이 특정 시점에만 실패하는 간헐 장애일 가능성을 높인다.

### 2) cron 자체 실패와 데이터 소스 실패를 다시 분리했다
브리핑이 실패했다고 해서 cron job 전체가 죽은 것은 아니었다. 실제로 브리핑 관련 job 상태는 `lastRunStatus: ok`로 남아 있었고, 사용자에게 도착한 실패 메시지도 시스템 전체 장애가 아니라 수집원 실패를 반영한 결과였다.

이 구분은 중요하다. 운영 리포트 문구만 보면 시스템이 멈춘 것처럼 보일 수 있지만, 실제로는 아래처럼 더 세분화해야 한다.

- 스케줄러는 실행됨
- 메시지 생성도 실행됨
- 다만 외부 요약 데이터를 받는 webhook이 실패함

### 3) 원인을 "n8n 서버 다운"보다 "workflow 내부 간헐 실패" 쪽으로 좁혔다
두 엔드포인트가 동일 시점에 함께 실패하고, 나중에는 둘 다 복구된 점을 보면 웹 서버나 DNS 같은 레이어보다 n8n 내부 workflow 실행 경로를 먼저 의심하는 게 합리적이다.

특히 응답 본문이 아래처럼 동일했다는 점이 힌트였다.

```text
{"message":"Error in workflow"}
```

이 메시지는 HTTP 레벨 통신 오류보다, webhook이 요청은 받았지만 내부 노드 실행 또는 의존 단계에서 예외가 발생했음을 시사한다.

## 핵심 설정 / 코드
이번에 운영 판단 근거로 삼은 응답 패턴은 아래처럼 정리할 수 있다.

```text
06:02
- /webhook/geeknews-summary -> 500, {"message":"Error in workflow"}
- /webhook/watchlist-summary -> 500, {"message":"Error in workflow"}
```

이후 동일한 브리핑 2번째 메시지를 다시 생성했을 때는 두 엔드포인트가 모두 정상 스키마를 반환했다.

````json
{
  "ok": true,
  "source": "geeknews",
  "generatedAt": "2026-04-09T23:20:55.266Z",
  "summaryText": "...",
  "items": [
    {
      "title": "...",
      "url": "https://..."
    }
  ]
}
````

운영적으로는 아래처럼 상태 판정 기준을 두는 편이 더 안전하다.

```yaml
incident_evaluation:
  scheduler_layer:
    - cron 실행 여부 확인
    - lastRunStatus와 delivery 상태 분리 확인
  data_source_layer:
    - webhook별 HTTP status 확인
    - 응답 본문이 workflow 예외인지 확인
    - 여러 엔드포인트 동시 실패 여부 비교
  recovery_layer:
    - 즉시 재호출 결과 저장
    - 몇 시간 뒤 재호출 결과와 비교
    - 단발 복구인지 안정화인지 구분
```

## 결과
이번 재점검으로 정리된 사실은 다음과 같다.

- 문제는 단순 오판이라기보다, 전날 장애가 "완전 해결"이 아니라 "일시적으로 응답 정상화"된 상태였다는 데 있었다.
- `watchlist-summary`, `geeknews-summary`는 아침 실행 시점에 함께 실패했고, 뒤늦게는 함께 정상화됐다.
- 따라서 브리핑 자동화의 약점은 cron 스케줄러보다 n8n workflow 실행 안정성 쪽에 더 가깝다.
- 운영 커뮤니케이션에서는 `복구 확인`과 `재발 방지 확인`을 같은 말로 쓰면 안 된다는 점이 분명해졌다.

추가로, 같은 패턴이 반복되면 다음 단계는 단순 재확인이 아니라 n8n workflow 내부 로그 기준의 근본원인 추적으로 넘어가야 한다. 예를 들어 외부 API 호출 실패, LLM 응답 파싱 예외, 마지막 응답 래핑 단계 오류 같은 공통 지점을 먼저 봐야 한다.

## 정리
운영 자동화에서 가장 위험한 표현 중 하나가 "지금 되니까 해결됐다"다. 특히 webhook 기반 파이프라인은 장애 시점과 점검 시점이 다르면 완전히 다른 모습을 보여준다.

이번 사례에서 배운 점은 세 가지다.

- 수동 재검증은 필요하지만, 그것만으로 안정화를 선언하면 안 된다.
- 아침 cron 실행 시점과 후속 점검 시점을 나눠 기록해야 간헐 장애를 잡을 수 있다.
- 같은 webhook이 같은 시각에 함께 실패했다면 프롬프트보다 workflow 공통 경로를 먼저 봐야 한다.

즉 이번 작업의 핵심은 새로운 기능 추가가 아니라, 브리핑 수집 장애를 "일시 복구"와 "실제 안정화"로 분리해 설명할 수 있는 운영 기준을 다시 세운 데 있었다.
