# OpenClaw Telegram 브리핑에서 JSON 노출과 모델 fallback 실패를 분리해 진단한 과정

#OpenClaw #Telegram #자동화 #운영 #LLM

## 한줄 요약
Telegram 브리핑 메시지의 JSON 노출과 운영 리포트 실패를 하나의 장애로 보지 않고, 출력 포맷 문제와 모델 fallback 체인 문제로 나눠 진단해 각각 수정했다.

## 배경
개인 운영 자동화에서 매일 아침 브리핑과 운영 리포트는 단순 알림이 아니라 시스템 상태를 빠르게 확인하는 인터페이스에 가깝다. 특히 OpenClaw 기반으로 Telegram 메시지를 생성할 때는 다음 두 가지가 동시에 중요하다.

- 최종 사용자에게 전달되는 메시지 포맷이 안정적일 것
- 모델 장애가 발생해도 fallback 체인이 예측 가능하게 동작할 것

이번에는 아침 브리핑 메시지 하단에 의도하지 않은 JSON이 노출됐고, 별도 운영 리포트는 아예 실패 메시지만 전달되는 상황이 발생했다. 겉으로 보면 하나의 장애처럼 보이지만, 실제로는 원인이 다른 두 문제가 겹쳐 있었다.

## 문제
문제는 크게 두 갈래였다.

첫째, Telegram 브리핑 본문 아래에 모델이 생성한 구조화 JSON이 그대로 붙어서 전송됐다. 즉, 사람이 읽어야 할 메시지와 시스템이 다루는 메타 출력이 분리되지 않았다.

둘째, 운영 리포트 생성 시 모델 fallback 체인에 등록된 여러 모델이 연속으로 실패했다. 이때 실패 원인이 단일하지 않았다.

- Gemini 계열 모델은 할당량 초과(rate limit)
- OpenAI 계열 모델은 인증 토큰 만료(auth)

이 상태에서는 “AI가 고장 났다”라고 뭉뚱그려 보기 쉽지만, 실제 운영 관점에서는 아래처럼 분리해서 봐야 한다.

1. 출력 포맷 제어 실패
2. 모델 선택 및 fallback 체인의 가용성 실패

이 둘을 섞어 보면 잘못된 대응을 하기 쉽다. 예를 들어 JSON 노출 문제를 모델 인증 문제로 오해하거나, 반대로 fallback 장애를 프롬프트만 수정해서 해결하려고 할 수 있다.

## 변경 내용
### 1) JSON 노출 문제를 프롬프트/출력 계약 문제로 분리
브리핑 메시지 자체는 의도한 형식으로 생성됐지만, 그 뒤에 모델이 추가한 JSON 메타데이터가 함께 전달됐다. 이 패턴은 `announce` 성격의 전달 단계에서 모델 출력 전체가 그대로 중계될 때 특히 문제가 된다.

핵심 대응은 단순했다.

- 최종 출력은 메시지 본문만 허용
- JSON 메타데이터, 코드 블록, 추가 설명 금지
- 사람이 읽는 출력과 시스템 내부 구조를 혼합하지 않도록 프롬프트를 명시적으로 수정

즉, 출력 포맷을 “좋아 보이는 텍스트”가 아니라 “엄격한 계약”으로 다뤘다.

### 2) fallback 실패를 모델별 원인으로 분해
운영 리포트 실패 메시지를 보면 여러 모델이 순차적으로 시도된 뒤 모두 실패했다. 이 로그가 의미하는 바는 명확하다.

- 기본 모델 또는 우선순위 상위 모델이 먼저 호출됨
- 실패 시 fallback 모델을 순서대로 시도함
- 당시 등록된 후보 모델 전체가 실패하면서 최종 실패로 종료됨

여기서 중요한 점은 “4개 모델이 모두 이상하다”가 아니라 “fallback 체인 전체의 가용성이 동시에 무너졌다”는 해석이다. 당시 실패 유형은 다음처럼 갈렸다.

- 한 축은 외부 모델 공급자의 quota 문제
- 다른 축은 인증 상태 만료 문제

이 분해가 되면 대응도 바로 갈린다.

- quota 문제는 사용량/시간대/모델 우선순위 조정 대상
- auth 문제는 재인증과 자격 상태 점검 대상

### 3) 사용자 관점에서 보이는 장애를 운영 관점 메시지로 재해석
실패 알림은 보통 “All models failed”처럼 요약돼 도착한다. 이 문구 자체는 맞지만, 운영자가 알고 싶은 정보는 훨씬 더 구체적이다.

- 어떤 모델이 먼저 호출됐는가
- 각 모델은 왜 실패했는가
- fallback은 정상적으로 수행됐는가
- 지금 해야 할 조치는 인증 갱신인가, quota 회복 대기인가

이번 정리에서는 에러 문장을 그대로 소비하지 않고, 실제 운영 행위로 번역하는 데 초점을 맞췄다.

## 핵심 설정 / 코드
브리핑 출력 계약은 아래처럼 텍스트 전용으로 강제하는 쪽이 안전하다.

````text
출력 규칙:
- 최종 출력은 사용자에게 보낼 메시지 본문만 작성한다.
- JSON, YAML, 메타데이터, 디버그 정보, 설명 문장을 추가하지 않는다.
- 백틱(```)으로 감싼 코드 블록을 출력하지 않는다.
- 아래 형식을 그대로 따른다.

📅 1) 날짜/요일
...
📰 4) 핵심 뉴스
...
````

운영 리포트 실패 상황은 아래처럼 읽는 것이 맞다.

```text
All models failed:
- google/gemini-2.5-flash -> rate_limit
- openai-codex/gpt-5.4 -> auth
- openai-codex/gpt-5.3-codex -> auth
- openai-codex/gpt-5.2 -> auth
```

이 로그는 “fallback이 동작하지 않았다”가 아니라, “fallback은 시도됐지만 후보 전부가 실패했다”는 의미다.

정리하면 운영 체크리스트는 아래처럼 분리된다.

```yaml
incident_triage:
  output_contract:
    - 사용자 메시지와 메타 출력이 분리되어 있는가
    - 전달 단계에서 summary/raw output이 그대로 노출되지 않는가
  model_availability:
    - primary 모델 quota 상태 확인
    - fallback 모델 인증 상태 확인
    - fallback 순서가 실제 운영 의도와 일치하는가
  recovery:
    - auth 오류면 재인증
    - rate_limit이면 대기 또는 우선순위 조정
```

## 결과
이번 수정으로 기대하는 효과는 분명하다.

- 아침 브리핑 메시지에서 JSON 같은 메타 출력이 다시 노출될 가능성을 낮춤
- 모델 장애를 “출력 문제”와 “가용성 문제”로 구분해 대응 가능
- fallback 실패 메시지를 보고 실제 조치 항목을 바로 판단할 수 있음
- 운영 리포트 장애 원인을 공급자별로 나눠 추적할 수 있음

특히 유의미했던 점은, 사용자 화면에 보이는 증상만 보고 한 번에 고치려 하지 않았다는 것이다. 출력 계약과 모델 가용성은 서로 다른 레이어이기 때문에, 이 둘을 분리해야 재발 방지에도 도움이 된다.

## 정리
LLM 자동화 운영에서 자주 놓치는 부분이 있다. 모델이 말을 잘 만드는지보다, 어떤 형식으로 출력해야 하는지와 실패했을 때 어떤 순서로 대체되는지가 더 중요할 때가 많다.

이번 이슈는 작은 메시지 노출 문제처럼 시작됐지만, 실제로는 다음 두 가지 운영 원칙을 다시 확인한 사례였다.

- 사용자에게 보이는 출력은 엄격한 계약으로 관리한다.
- fallback은 “설정돼 있다”보다 “실패 원인을 분리해 해석할 수 있다”가 더 중요하다.

Telegram 같은 채널 자동화는 겉보기에는 간단하지만, 프롬프트 설계·전달 계층·모델 인증·quota 상태가 동시에 얽힌다. 그래서 장애가 발생했을 때는 한 문장의 실패 메시지보다, 레이어를 나눠 보는 습관이 더 실용적이다.
