# Daily 브리핑 구조를 3메시지로 분리한 날

#Daily브리핑 #자동화 #GeekNews #운영리포트 #가비서

> _이 글은 하루 동안 진행한 작업을 AI로 정리한 초안을 바탕으로, 사람이 검수·수정해 게시하는 기록입니다._

매일 아침 받아보는 브리핑은 정보가 많아질수록 오히려 읽기 어려워진다. 이날은 가비서의 Daily 브리핑 구조를 다시 정리하면서, **사용자용 정보와 운영 정보를 한 메시지 안에 섞지 않는 방향**으로 손을 봤다.

처음 문제의식은 단순했다. 날씨, 일정, 뉴스처럼 바로 소비하는 정보 사이에 운영 리포트가 붙으니 흐름이 끊겼다. 브리핑은 브리핑답게 읽혀야 하고, 운영 상태는 필요할 때 확인하면 된다. 그래서 메인 브리핑과 부가 정보를 분리하는 쪽으로 구조를 다시 설계했다.

동시에 기존 1번째 메시지에 들어가 있던 관심 주제 링크와 트렌드 키워드, 그리고 2번째 메시지의 GeekNews 상세 브리핑이 어떤 식으로 배치되어야 읽기 더 자연스러운지도 함께 조정했다. 핵심은 양을 줄이는 게 아니라, **메시지별 역할을 더 분명하게 만드는 것**이었다.

## 이번에 한 일

- Daily 브리핑에서 운영 리포트가 본문 흐름을 깨는 문제를 점검했다.
- 운영 리포트를 본문 안에 두지 않고, **3번째 별도 메시지**로 분리하는 방향을 확정했다.
- 1번째 메시지는 날짜, 날씨, 일정, 핵심 뉴스 중심의 **메인 브리핑**으로 정리했다.
- 기존 1번째 메시지에 있던 관심 주제 링크와 트렌드 키워드는 2번째 메시지로 옮기는 구조를 정리했다.
- 기존 2번째 메시지의 **GeekNews 상세 브리핑은 유지**하면서, 확장 정보 메시지 역할로 재배치했다.
- 관련 cron job 구성을 수정하고 수동 실행까지 점검해 실제 출력 흐름을 확인했다.

## 왜 구조를 바꿨나

기존 브리핑은 한 번에 많은 내용을 담으려다 보니, 성격이 다른 정보가 한 메시지에 섞이는 문제가 있었다.

특히 아래 두 가지가 계속 걸렸다.

- **운영 리포트가 본문 흐름을 끊는다**
- **메인 정보와 확장 정보의 경계가 흐리다**

그래서 앞으로는 아래처럼 역할을 분명히 나누기로 했다.

- **1번째 메시지**: 오늘 바로 확인해야 하는 핵심 정보
- **2번째 메시지**: 관심 주제, 트렌드 키워드, GeekNews처럼 여유 있을 때 보는 확장 정보
- **3번째 메시지**: 운영 상태 확인용 부록

이렇게 나누고 나니 브리핑의 목적도 훨씬 선명해졌다.

## 조정 과정에서 확인한 점

이번 구조 조정에서는 메시지를 나누면 토큰 사용량이 크게 늘지 않을까 하는 점도 같이 검토했다. 하지만 실제로는 같은 정보를 담는다면 메시지 수보다 **전체 텍스트 양**이 더 큰 변수였고, 구조를 명확히 하는 쪽의 이점이 더 컸다.

또한 운영 리포트는 평소엔 짧게, 이상이 있을 때만 자세하게 쓰는 방식이 맞다는 점도 정리했다. 결국 운영 정보는 중요하지만, 메인 브리핑의 가독성을 해치지 않는 위치에 있어야 했다.

## 이번 작업에서 얻은 점

이번 정리에서 가장 크게 느낀 건, 자동화는 기능을 많이 넣는 것보다 **읽는 흐름을 먼저 설계하는 것**이 더 중요하다는 점이다.

브리핑도 마찬가지다. 많이 담는다고 좋은 게 아니라, **읽는 사람이 어떤 순서로 소비할지를 먼저 정리해야 한다.** 메시지 구조를 나누는 일은 단순한 포맷 수정이 아니라, 결국 사용 경험을 다듬는 작업에 가깝다.
