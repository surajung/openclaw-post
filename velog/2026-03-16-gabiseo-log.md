# OpenClaw Daily 브리핑 자동화와 n8n Docker 문제를 함께 정리한 날

OpenClaw를 실제로 굴리다 보면, 기능을 붙이는 것보다 먼저 운영이 흔들리지 않게 만드는 일이 더 중요해진다. 이날은 딱 그런 날이었다. Telegram 응답 문제의 원인을 좁히고, Daily 브리핑 자동화를 확정하고, 동시에 n8n Docker 구성을 다시 안정화하는 작업이 한꺼번에 이어졌다.

특히 인상적이었던 건, 각각 별개의 문제처럼 보이던 것들이 결국은 하나의 운영 흐름으로 연결된다는 점이었다. 브리핑 자동화를 만들려면 캘린더와 메시지 전달이 안정적이어야 하고, 자동화 파이프라인이 제대로 돌려면 Docker와 파일 접근 설정도 흔들리면 안 된다. 결국 “기능 추가”와 “운영 안정화”는 따로 갈 수 없었다.

## 이번에 한 일

- Telegram 무응답 이슈를 로그와 시스템 절전 패턴 기준으로 확인하고, 절전 영향 가능성을 높게 봤다.
- OpenClaw를 `2026.3.11`에서 `2026.3.12`로 업데이트하고 상태를 점검했다.
- Telegram 그룹 `가비서 - Daily`를 대상으로 Daily 브리핑 자동화를 확정했다.
- Google Calendar 읽기 전용 연동을 마무리하고, 오늘 일정 조회 스크립트와 npm 스크립트를 정리했다.
- 초기 `primary` 캘린더만 보던 구조를 전체 캘린더 조회 방식으로 보정했다.
- `n8n-docker` 환경에서 반복되던 Compose/볼륨/파일 접근 문제를 원인별로 정리하고 해결 방향을 굳혔다.

## 왜 이 작업이 중요했나

Daily 브리핑은 겉으로 보기엔 단순한 메시지 자동화 같지만, 실제로는 몇 가지 전제가 맞아야 성립한다.

- 메시지 채널이 안정적으로 응답할 것
- 일정 데이터가 빠지지 않고 조회될 것
- n8n 같은 자동화 스택이 재시작 이후에도 상태를 유지할 것

이번 작업은 바로 그 기반을 다지는 쪽에 가까웠다. 단순히 “브리핑을 만들었다”보다, 앞으로도 계속 유지될 수 있는 자동화 구조를 만든 날이라고 보는 편이 맞다.

## 이슈와 해결

### Telegram 그룹 응답 문제
- `channels.telegram.groupPolicy="allowlist"`일 때 그룹 chat_id를 명시하지 않으면 응답 자체가 스킵된다는 점을 확인했다.
- Bot 권한 문제와 별개로, OpenClaw 설정 상 허용 목록이 정확해야 한다는 학습이 있었다.

### 캘린더 일정 누락
- 처음에는 `primary` 캘린더만 조회해 일정이 일부 빠졌다.
- 실제 사용 기준에서는 가족/공유 캘린더까지 포함해야 의미가 있으므로, 전체 캘린더 조회 방식으로 수정했다.

### n8n Docker/Colima 문제
- 이 환경에서는 `docker compose`가 아니라 `docker-compose`를 써야 안정적으로 동작한다는 점을 다시 확인했다.
- Compose project identity 충돌 때문에 `No such container` 류의 문제가 발생했고, `name: n8n-prod`처럼 명시적인 project name을 두는 게 중요했다.
- 컨테이너가 `root`로 도는 상황에서는 n8n 데이터 경로가 `/root/.n8n`이라는 점을 놓치기 쉬웠고, 올바른 볼륨 매핑으로 재시작 후 설정 유실 문제를 해결했다.
- `N8N_RESTRICT_FILE_ACCESS_TO`는 콤마가 아니라 세미콜론 구분이어야 한다는 점도 함께 정리했다.

## 이번 작업에서 얻은 점

자동화는 기능 자체보다도, 운영 환경과 연결되는 경계 조건을 먼저 이해해야 오래 간다. 특히 Docker, 파일 경로, 채널 정책 같은 설정들은 잘 되면 티가 안 나지만, 한 군데라도 어긋나면 전체 흐름이 쉽게 무너진다.

또 하나 느낀 건, 브리핑 자동화 같은 사용자-facing 기능도 결국은 캘린더 연동, 메시지 정책, n8n 안정성 같은 바닥 작업 위에서만 의미가 생긴다는 점이다.
