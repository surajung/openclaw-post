# 매일 아침 브리핑을 ‘읽기 흐름’ 중심으로 다시 쪼갠 하루

#OpenClaw #가비서 #작업일지 #자동화 #운영

> _이 글은 하루 동안 진행한 작업을 AI로 정리한 초안을 바탕으로, 사람이 검수·수정해 게시하는 기록입니다._

아침 브리핑 자동화를 운영하다 보면, 정보가 많아질수록 “무엇을 먼저 읽게 할 것인가”가 더 중요해집니다. 같은 내용이라도 배치가 어색하면 핵심 정보 전달력이 떨어지고, 운영 상태 같은 부가 정보가 본문 흐름을 끊기도 합니다.

이번 작업의 초점은 단순히 내용을 추가하는 것이 아니라, **브리핑 메시지의 역할을 분리해 읽는 순서를 자연스럽게 만드는 것**이었습니다. 동시에 워치리스트/GeekNews 같은 외부 소스 연동도 유지하면서, 실패 시 처리 방식까지 함께 정리했습니다.

## 이번에 한 일

- Daily 브리핑 구조를 3개 메시지 역할로 분리
  - 1번: 메인 브리핑(날짜/날씨/일정/핵심 뉴스)
  - 2번: 확장 정보(워치리스트, 트렌드 키워드, GeekNews)
  - 3번: 운영 리포트(정상 시 짧게, 이상 시 상세)
- 2번 메시지 생성 규칙 강화
  - `watchlist-summary`, `geeknews-summary` webhook을 함께 호출
  - 각 소스의 `summaryText` 우선 사용, 링크 목록 개수 제한
  - 실패 시 대체 문구로 안전하게 폴백
- 운영 리포트는 사용자용 본문과 분리해 “부록” 성격을 명확히 함

## 왜 이렇게 바꿨는지 / 핵심 판단

핵심은 **정보의 중요도와 소비 맥락 분리**입니다.

- 메인 브리핑은 바로 읽고 의사결정에 쓰는 정보
- 확장 정보는 여유 있을 때 보는 탐색형 정보
- 운영 리포트는 필요할 때 확인하는 상태 정보

이렇게 나누면 같은 토큰을 써도 체감 가독성이 올라가고, 운영 이슈가 없을 때 채널 피로도도 줄일 수 있습니다.

## 이슈와 해결

- 이슈: 운영 상태 정보가 메인 브리핑 본문과 섞여 톤이 충돌
- 해결: 운영 리포트를 별도 3번째 메시지로 분리

- 이슈: 외부 요약 소스 실패 시 메시지 품질이 흔들릴 수 있음
- 해결: 소스별 실패 문구를 명시해 브리핑 전체 흐름을 유지

- 이슈: 확장 정보가 길어지면 읽기 부담 증가
- 해결: 링크 개수 상한, 문단 간격, 섹션 고정 포맷으로 밀도 관리

## 이번 작업에서 얻은 점

브리핑 자동화는 “무엇을 수집하느냐”보다 “어떤 순서로 보여주느냐”가 실제 만족도를 크게 좌우합니다. 특히 운영 정보는 정확히 중요하지만, 모든 날 전면에 둘 필요는 없습니다. 상태 정보는 뒤로, 핵심 정보는 앞으로 두는 기본 원칙이 유효했습니다.

## 다음 단계

- 2번 메시지(확장 정보)의 길이 상한을 데이터 기반으로 추가 튜닝
- 일정 기간 운영 후, 실제 읽힘/반응 기준으로 포맷 미세 조정
