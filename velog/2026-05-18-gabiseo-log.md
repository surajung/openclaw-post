# OpenClaw에서 텔레그램 응답이 끊겼을 때 가장 먼저 확인할 설정

#OpenClaw #Telegram #운영 #장애대응

## 한줄 요약
OpenClaw의 텔레그램 응답 장애를 네트워크 문제가 아니라 \`channels.telegram.enabled\` 설정과 게이트웨이 기동 로그를 기준으로 진단하고, 채널 재활성화 후 실제 플러그인 로드까지 확인했다.

## 배경
아침 브리핑 메시지는 계속 도착하는데, 텔레그램에서 직접 말을 걸었을 때는 응답이 오지 않는 상태가 발생했다.

이 경우 겉으로 보면 "텔레그램이 죽었다"로 보이기 쉽지만, 실제로는 송신 자동화와 인바운드 대화 처리가 서로 다른 경로를 탈 수 있다. 그래서 이번 점검은 Telegram API 자체보다, 채널 활성화 상태와 런타임 플러그인 로드 여부를 먼저 확인하는 순서로 진행했다.

## 문제
증상은 단순했지만 원인 후보는 여러 갈래였다.

- 텔레그램 채널이 설정상 비활성화됐을 수 있다.
- 게이트웨이가 재기동되면서 텔레그램 플러그인이 빠진 채 올라왔을 수 있다.
- 브리핑 cron 전송은 살아 있어도, 인바운드 응답 경로만 막혔을 수 있다.

즉, "메시지가 일부 간다"는 사실만으로 채널 전체가 정상이라고 판단하면 안 되는 상황이었다.

## 변경 내용
- 설정 파일에서 \`channels.telegram.enabled\` 값을 먼저 확인해, 인바운드 응답 불가를 채널 비활성화 문제로 좁혔다.
- 게이트웨이 로그에서 \`config change detected (channels.telegram.enabled)\` 이벤트와 이후 재시작 흐름을 확인했다.
- 재기동 뒤 플러그인 목록에 \`telegram\`이 실제로 포함되는지, 그리고 provider 시작 로그가 찍히는지까지 검증했다.
- 마지막으로 \`sendMessage ok\` 로그를 확인해, 단순 설정 변경이 아니라 실행 중 런타임이 정상 상태로 복귀했는지 확인했다.

이 과정에서 중요한 포인트는 설정 파일 한 줄만 보고 끝내지 않았다는 점이다. 채널 토글, 게이트웨이 재기동, 플러그인 로드, 송신 로그까지 이어서 봐야 실제 복구 여부를 판단할 수 있다.

## 핵심 설정 / 코드
공개 초안에서는 민감값을 제거하고, 문제를 재현한 핵심 설정만 남기면 아래 정도로 요약할 수 있다.

\`\`\`json
{
  "channels": {
    "telegram": {
      "enabled": true,
      "dmPolicy": "pairing",
      "groupPolicy": "allowlist",
      "streaming": {
        "mode": "partial"
      }
    }
  }
}
\`\`\`

장애 분석에서 실제로 중요했던 건 토큰이나 상세 허용 목록이 아니라, 이 \`enabled\` 플래그와 게이트웨이 로그의 연결이었다.

\`\`\`\`text
2026-05-16T10:11:10+09:00 [reload] config change detected; evaluating reload (channels.telegram.enabled)
2026-05-16T10:11:10+09:00 [gateway/channels] restarting telegram channel
...
2026-05-18T06:23:43+09:00 [gateway] http server listening (..., telegram; 3.1s)
2026-05-18T06:23:44+09:00 [telegram] [default] starting provider
2026-05-18T06:23:55+09:00 [telegram] sendMessage ok
\`\`\`\`

이 조합이 말해주는 것은 명확하다.

- 채널 설정 변경이 실제 런타임에 반영됐다.
- 재기동 이후 텔레그램 플러그인이 다시 로드됐다.
- 최소한 송신 경로는 정상 상태로 복귀했다.

## 결과
이번 점검으로 텔레그램 응답 불가의 직접 원인을 네트워크나 API 장애가 아니라 채널 비활성화 설정으로 특정할 수 있었다.

또한 복구 판단도 "설정을 다시 켰다" 수준에서 멈추지 않고, 아래 순서로 검증했다.

- 게이트웨이 재시작 확인
- 플러그인 목록에 \`telegram\` 포함 확인
- provider 시작 로그 확인
- \`sendMessage ok\` 확인

결과적으로 브리핑 자동화와 대화형 응답이 서로 다른 경로를 가질 수 있다는 점이 드러났고, 운영 체크리스트도 "메시지가 갔는가"에서 "채널이 로드됐는가"까지 확장할 필요가 생겼다.

## 정리
텔레그램 응답 장애를 볼 때 가장 먼저 확인할 것은 Telegram API 상태보다 OpenClaw 내부 채널 설정이다. 특히 \`channels.telegram.enabled\`처럼 작은 토글 하나가 인바운드 응답 전체를 막을 수 있다.

운영 관점에서 이번 작업이 남긴 교훈은 두 가지다. 첫째, 브로드캐스트 메시지가 간다고 해서 채널 전체가 정상이라고 보면 안 된다. 둘째, 복구는 설정 변경 자체가 아니라 플러그인 로드와 실제 송신 로그까지 확인해야 끝난다.

앞으로 비슷한 장애가 생기면, 설정 플래그 확인 → 게이트웨이 재기동 로그 확인 → 텔레그램 플러그인 로드 확인 → 실사용 테스트 순서로 점검하는 편이 가장 빠르다.
